# Give an agent a task

Start with a Work item, a specific deliverable and a person who can judge the result. A document edit is a good first task. An agent can help in a project that has no code repository.

## Write a brief someone can review

For example, “Move the opening meeting from Monday to Wednesday in the visitor guide. Keep the time, meeting point and all other wording. Show the proposed change for review.”

Link or identify the exact page, describe what the agent may change, and say when it should ask a question. For this example, it should ask if the page contains two different Monday meetings.

## Choose the worker

The Owner is the person accountable for the outcome. On a Home with registered agent workers, **Working on it** identifies the worker. The current private pilot shows **Assignee**. Assigning a name or copying the brief does not start a model. If your Home has no connected agent runner, the brief is still usable for a manual handoff.

## Does each agent need a moon?

No. A moon gives a worker its own ship address under a parent planet. Use one when the worker needs to communicate as its own Urbit ship. A Home can also identify a registered agent and bind it to a worker runtime. The operator connects that runtime to a local model or a compatible hosted provider. Neither a moon's parent planet nor a model name grants access to a project. [How Urbit IDs work](https://docs.urbit.org/urbit-id/what-is-urbit-id)

Grant the worker only the project, document and actions this task requires. Keep a human owner and choose a reviewer. Never share a person's ship sign-in code with a model.

## Review the result

Ask for the exact proposed edit. Compare it with the original and request a revision if anything else changed. The reviewer checks the current document and accepts the exact change. Mark the Work done after you can reopen the accepted result.

The complete assign, clarify, revise and accept journey is still being tested. A model response or a comment alone does not change the saved document.
